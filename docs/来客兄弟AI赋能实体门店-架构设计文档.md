## 一、架构约束分析

设计任何架构之前，先理清边界条件。以下约束直接决定了架构形态：

| 约束 | 影响 |
|------|------|
| **团队 1-2 人，5 个项目并行** | 不可引入多服务协作开销，不可要求基础设施复杂度 |
| **P1 交付截止 8 月 11 日** | 不可推翻重来，必须基于已有代码演进 |
| **流量初期低，峰值取决于广告投放** | 不需要弹性伸缩，单进程 + SQLite 够用 |
| **微信生态是核心入口** | H5 + 小程序两套前端，后端 API 必须统一 |
| **已有 CMS 项目（React + MySQL）在建** | 未来可能共享数据，设计时预留整合接口 |
| **服务器与原有项目共享同一台机器** | 端口/域名隔离已验证可行，不引入新硬件 |

**核心推论**: 对于这个规模的项目，架构的主要敌人不是性能瓶颈，而是**认知负担**——团队没有精力同时理解多套服务、多套数据库、多套部署。架构的第一优先级是**降低理解成本**。

## 二、领域分析 — 限界上下文

通过事件风暴识别出 5 个限界上下文（Bounded Context）：

```
┌─────────────────────────────────────────────────────────────┐
│                    来客兄弟 业务领域                          │
│                                                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐       │

│  │              │  │              │  │              │       │
│  │ · 城市选择    │  │ · 6模块预约   │  │ · 含AI量检测  │       │
│  │ · 内容展示    │←─│ · 表单校验    │  │ · 分享裂变    │       │
│  │ · 课程大纲    │  │ · 状态流转    │  │ · 海报生成    │       │
│  │ · 讲师/FAQ   │  │ · 数据入库    │  │ · 结果分析    │       │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘       │
│         │                 │                 │               │
│         │    ┌────────────┼────────────┐    │               │
│         │    │            │            │    │               │
│         ▼    ▼            ▼            ▼    ▼               │
│  ┌──────────────┐                  ┌──────────────┐         │
│  │ Notification │                  │    Admin     │         │
│  │   通知上下文  │                  │   管理上下文  │         │
│  │              │                  │              │         │
│  │ · 多渠道分发  │                  │ · 数据看板    │         │
│  │ · 通知日志    │                  │ · 预约管理    │         │
│  │ · 失败重试    │                  │ · 状态流转    │         │
│  └──────────────┘                  └──────────────┘         │
└─────────────────────────────────────────────────────────────┘
```

**上下文关系**：

| 上游 → 下游 | 关系类型 | 说明 |
|-------------|----------|------|
| Landing Page → Booking | 共享内核 | 表单字段结构共享，但不共享业务规则 |
| Booking → Notification | 发布/订阅 | Booking 发布"预约已创建"事件，Notification 订阅 |
| Booking → Admin | 开放主机 | Admin 直接查询 Booking 的数据库 |
| Engagement → Booking | 客户-供应商 | 检测完成后可引导预约，弱耦合 |

**为什么不是微服务？** 5 个上下文虽然逻辑上独立，但物理上：
- 除 Notification 外，其他上下文没有独立的部署需求
- 上下文间没有需要解耦的团队边界（全是同一个人维护）
- 引入服务间通信（HTTP/gRPC/消息队列）增加的复杂度远超收益

## 三、架构决策记录（ADR）

### ADR-001：选择模块化单体而非微服务

**状态**：已接受

**背景**：项目包含 5 个限界上下文（落地页、预约、互动、通知、管理）。需要决定物理部署形态。

**方案对比**：

| 维度 | 模块化单体 | 微服务 |
|------|-----------|--------|
| 部署复杂度 | 1 个进程，1 个 systemd 服务 | 5 个进程，5 个 systemd 服务 + 服务发现 |
| 调试难度 | 单步调试，一次打断点看清全流程 | 需要分布式追踪 |
| 数据库事务 | SQLite 原生 ACID | 分布式事务或最终一致性 |
| 运维成本 | 1 个日志文件，1 个部署脚本 | 5 套日志，5 个部署脚本，1 个编排工具 |
| 独立扩缩 | 不可（但当前不需要） | 可 |
| 团队并行 | 不可（但团队只有 1-2 人） | 可 |
| 故障隔离 | 弱（一个模块 OOM 全挂） | 强 |

**决策**：模块化单体。在代码层面用目录边界隔离上下文，但运行时共享同一进程。

**代价**：
- 放弃独立扩缩 → 可接受，流量初期不需要
- 放弃故障隔离 → 可接受，Express 有全局 uncaughtException 兜底
- 代码耦合风险 → 通过 ESLint import 规则强制模块间依赖方向

**可逆性**：高。如果未来某个模块需要独立部署（如通知服务成为独立微服务），只需把 `server/notify.js` 抽出为独立进程，接口不变。

### ADR-002：前端选择原生 HTML/CSS/JS 而非框架

**状态**：已接受

**背景**：落地页需要轻量、快速、在微信内置浏览器中兼容性好。同时后续有小程序版本。

**方案对比**：

| 维度 | 原生三件套 | React/Vue SPA | Astro/SSG |
|------|-----------|---------------|-----------|
| 构建步骤 | 零 | webpack/vite | 需要 |
| 文件体积 | 56KB（压缩后 ~20KB） | 100KB+ (含 runtime) | 类似原生 |
| 微信浏览器兼容 | 极好（无 JSX/虚拟 DOM） | 偶发兼容问题 | 好 |
| 学习成本 | 零 | 需要 React/Vue 生态知识 | 需要 Astro 概念 |
| 首屏速度 | 即时（无 JS 初始化） | 需要 hydration | 好 |
| 小程序复用 | 不可直接复用 | Taro 可编译 | 不可 |

**决策**：原生 HTML/CSS/JS。理由——P1 阶段的核心目标是**快**，不是**工程化**。等 P5 小程序阶段，直接用 Taro 重写业务逻辑（预约表单、小游戏），但落地页保持原生。

**代价**：
- 不可复用代码到小程序 → 可接受，小程序需要 `wx.*` API 重写
- 没有组件化 → 可接受，页面组件粒度粗（9 个 Section），复制粘贴成本低于框架学习成本
- 状态管理靠全局变量和 DOM → 可接受，页面交互简单

**可逆性**：中。如果要迁移到框架，HTML 模板可以直接搬到 JSX/Vue template。

### ADR-003：数据库选择 SQLite（sql.js）而非 MySQL

**状态**：已接受

**背景**：需要持久化预约数据。已有 CMS 项目使用 MySQL，但本项目需要快速启动。

**方案对比**：

| 维度 | SQLite (sql.js) | MySQL |
|------|-----------------|-------|
| 安装依赖 | 零（纯 JS，npm install 即用） | 需要 MySQL 服务 + 客户端库 |
| 部署步骤 | 零（自动创建 .db 文件） | 建库、建用户、授权、迁移脚本 |
| 备份 | cp .db 文件 | mysqldump + 定时任务 |
| 并发写入 | 低（单写锁） | 高 |
| 与 CMS 整合 | 需要迁移脚本 | 天然同一数据库 |

**决策**：SQLite (sql.js)。P1-P4 阶段数据量小、并发低，SQLite 够用。P5 阶段如果小程序带来高并发，或需要与 CMS MySQL 整合，执行迁移。

**代价**：
- 放弃高并发写入 → 可接受，预约表单不是秒杀场景
- 迁移成本 → SQLite → MySQL 迁移已预留接口（db.js 的 `getOne/getAll/run` 抽象层），迁移只需改 db.js 内部实现

**可逆性**：高。已在 db.js 中抽象数据库操作，迁移到 MySQL 时 routes.js 和 notify.js 代码零改动。

### ADR-004：通知采用异步 Agent 模式而非消息队列

**状态**：已接受

**背景**：预约提交后需要通知需求方（企微/Webhook/邮件），通知不能阻塞用户响应。

**方案对比**：

| 维度 | setImmediate 异步 | 消息队列（Redis/RabbitMQ） |
|------|-------------------|---------------------------|
| 基础设施 | 零（Node.js 原生） | 需要 Redis/RabbitMQ 服务 |
| 消息可靠性 | 低（进程重启丢失） | 高（持久化） |
| 实现复杂度 | 10 行代码 | 需要生产者、消费者、DLQ |
| 运维成本 | 零 | 需要监控队列积压 |

**决策**：`setImmediate` + 数据库日志。当前场景下，通知失败不是灾难性故障（运营人员可以通过管理后台手动查看预约），因此不需要消息队列的可靠性保证。

**代价**：
- 进程重启时飞行中的通知丢失 → 可接受，预约数据已在数据库，可补发
- 无重试机制 → 后续可加（基于 notify_logs 表实现 cron 重试）

**可逆性**：中。后续如果通知可靠性要求提升，notify.js 的接口已预留，替换为消息队列生产者在 notify.js 内部修改即可。

### 4.2 模块内部边界

当前代码的依赖关系是健康的（routes → db/notify，单向），但缺少城市配置层。建议增加：

```
server/
├── index.js              # 进程入口，组装依赖
├── routes.js             # 路由薄层（参数校验 → 委托给 service）
│
├── services/             # 业务逻辑层（新增）
│   ├── booking.service.js    # 预约生命周期管理
│   ├── contact.service.js    # 留资管理
│   └── aiTest.service.js     # AI检测记录
│
├── data/                 # 数据访问层（重构自 db.js）
│   ├── connection.js         # sql.js 初始化 + 连接管理
│   ├── booking.repo.js       # 预约表 CRUD
│   ├── contact.repo.js       # 留资表 CRUD
│   └── notify.repo.js        # 通知日志表 CRUD
│
├── notify/               # 通知模块（重构自 notify.js）
│   ├── index.js              # 统一通知入口
│   ├── channels/
│   │   ├── webhook.js        # Webhook 渠道
│   │   ├── wecom.js          # 企业微信渠道
│   │   ├── email.js          # 邮件渠道
│   │   └── console.js        # 控制台/文件日志
│   └── formatter.js          # 消息格式化
│
├── city.config.js        # 城市配置（新增）
│   # 集中管理城市列表、对应活动场次、社群二维码等
│
└── admin/                # 管理后台（不变）
    └── index.html
```

**关键设计决策**：Route → Service → Repository 三层分离。

当前 `routes.js` 直接调用 `db.createBooking()`——这在项目初期可行，但随着 6 个模块的差异化逻辑增加（如 M3 游学需要关联客服，M4 展厅需要生成确认函），需要 Service 层承载业务逻辑。

### 4.3 城市配置层设计

需求要求每个城市有独立落地页。与其为每个城市维护一个 HTML 文件，不如用一个配置驱动：

```javascript
// server/city.config.js
module.exports = {
  beijing: {
    name: '北京',
    heroTitle: '北京实体门店，要么AI化，要么被AI化',
    activeModules: ['community', 'salon', 'tour', 'visit', 'course', 'enterprise'],
    salon: {
      dates: ['2026-08-15', '2026-08-22'],
      venue: '北京市朝阳区XX大厦',
      maxSeats: 50,
    },
    communityQR: 'https://cdn.lkxdai.com/qr/beijing-community.png',
  },
  shanghai: { /* ... */ },
  // ...8 个城市
};
```

前端通过 URL 路径 `/city/beijing` 或 URL 参数 `?city=beijing` 获取城市代码，然后在初始化时从 `/api/city-config?city=beijing` 加载配置。

## 五、数据架构

### 5.1 数据主权

```
Booking Context ──拥有──▶ bookings 表
                         contacts 表

Engagement Context ──拥有──▶ ai_tests 表

Notification Context ──拥有──▶ notify_logs 表
```

所有上下文共享同一个 SQLite 文件。但每个上下文有自己"拥有"的表，其他上下文通过 Repository 访问（而非直接 SQL）。

### 5.2 聚合根

```javascript
// Booking 聚合根（唯一入口）
Booking {
  id, type, name, phone, city,
  company, note, source, status,
  createdAt, updatedAt
}

// 聚合不变量：
// 1. status 只能沿 pending → contacted → confirmed 单向流转
// 2. cancelled 可从任意非终态转入
// 3. phone 必须通过正则校验
```

**设计选择**：当前采用单表 + `type` 字段区分 6 种预约，而非 6 张独立表。理由：
- 6 种预约的核心字段 80% 重叠，多表会导致大量重复的 CRUD 代码
- 差异化字段用 `note` 或后续加的 `extra` (JSON) 字段存储
- 查询时按 `type` 过滤，SQLite 单表扫描性能完全够用

**反模式警告**：不要用 `extra` JSON 字段做查询条件。如果后续需要按"门店类型"或"预算区间"筛选，应新建独立字段。

### 5.3 与 CMS 项目的数据关系

```
┌─────────────────────┐       ┌─────────────────────┐
│  来客兄弟落地页项目   │       │  来客兄弟 CMS 项目    │
│  (SQLite)           │       │  (MySQL)            │
│                     │       │                     │
│  bookings ──────────┼──?──▶│  leads / customers  │
│  contacts ──────────┼──?──▶│  contacts           │
│  ai_tests           │       │                     │
└─────────────────────┘       └─────────────────────┘
```

**当前策略**：两套数据库独立。预约数据不自动同步到 CMS。

**未来整合路径**：如果需求方要求预约数据进入 CMS 的 CRM 系统，有两种方式：
1. **推送模式**：Booking Service 创建预约后，通过 Webhook 推送到 CMS API
2. **拉取模式**：CMS 定时调用 `/api/bookings?since=2026-08-01` 拉取增量数据

推荐推送模式——实时性更好，且不暴露内部表结构。

## 八、质量属性分析

| 属性 | 当前方案 | 风险 | 对策 |
|------|---------|------|------|
| **可用性** | systemd auto-restart，进程挂了 5 秒自愈 | 服务器宕机则全挂 | 单点，无冗余。接受。 |
| **性能** | SQLite 内存模式 + 单页 HTML，响应 <50ms | 并发超 100 QPS 时 SQLite 单写锁成为瓶颈 | 大概率不会。如发生，P6 迁 MySQL。 |
| **安全性** | token 鉴权 + 手机号校验 | token 明文传输（HTTP） | P6 配置 HTTPS + Let's Encrypt |
| **可维护性** | 代码量约 2000 行，单人可全量理解 | 无自动化测试 | P1 阶段手动测试即可，P6 补测试 |
| **可观测性** | 控制台日志 + 文件日志 + Nginx access log | 无告警 | 后续接入企微通知异常即可 |

## 九、架构原则总结

1. **简单优先于灵活**。60% 的"未来可能需要"永远不会发生。只为已确认的 Phase 1-6 需求设计。
2. **代码边界优先于物理边界**。用目录结构隔离上下文，不用进程边界。
3. **数据归属明确**。每个表只有一个"拥有者"上下文，其他上下文通过 Repository 访问。
4. **降级是功能，不是补丁**。本地 localStorage 降级从 Day 1 就设计进去，不是上线后加的。
5. **可逆决策优先**。SQLite→MySQL、单进程→微服务、原生→框架——每条路径都预留了接口，改主意时不需要重写。
